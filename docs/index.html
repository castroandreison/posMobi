Visão Geral

PósMobi é a plataforma de monitoramento pós-venda de estações de recarga Intelbras. Ela consome a API pública Intelbras (CS) via um proxy próprio, exibindo o estado das estações, logs OCPP, e permitindo o envio e monitoramento de atualizações de firmware.

Última atualização da documentação:

React 19 Vite 6 Tailwind 4 Python Recharts Axios

Funcionalidades principais

  • Dashboard — KPIs, gráfico de carregadores por modelo, tabelas por modelo com filtros avançados e modal de logs de falha.
  • Firmware — upload de firmware por carregador, cadastro de URLs/versões por modelo, monitoramento em tempo real do status do upload.
  • Histórico — tabela paginada de atualizações de firmware com período, gráfico de barras empilhadas de versões por modelo.
  • Log — visualização de logs OCPP (Cloud Intelbras), busca, filtro por estação e download.
  • Login — página de autenticação com credenciais Intelbras.

Backend — Servidor & Proxy

O backend (backend/server.py) roda um ThreadingTCPServer na porta 8000 usando SimpleHTTPRequestHandler. Abre o navegador automaticamente ao iniciar.

Login automático

Ao iniciar (ou quando o token expira), chama POST {BASE_URL}/api/v1/login com as credenciais do .env, guardando em memória TOKEN, TENANT_UUID e TENANT_PK. Suporta backoff exponencial e tratamento de rate-limit (HTTP 429 com retryAfterSeconds).

Proxy genérico

Toda requisição /api/* é repassada a {BASE_URL}/api/*, com headers de autenticação: Api-Key, Platform, Authorization: Bearer {token}, authorization, tenant_uuid, x-tenant-uuid, tenant_pk, x-tenant-pk.

Para as rotas de firmware/operações (/api/v1/firmware-update-history, /api/v1/operations/) o header Platform é trocado para MOBILE, pois essas rotas só funcionam na API móvel.

Frontend buildado

Se frontend/build existir, ele é servido como conteúdo estático na raiz, com Cache-Control: no-cache em todas as respostas.

Respostas JSON/proxy incluem Access-Control-Allow-Origin: *; OPTIONS responde 204 liberando GET/POST/PUT/DELETE.

Backend — Configuração (.env)

O arquivo backend/.env é lido por config.py (parse manual, sem dependência). Chaves obrigatórias:

BASE_URL=https://cs.intelbras-cve-pro.com.br
API_KEY=COLE_SUA_API_KEY
PLATFORM=API
EMAIL=seu-email@empresa.com
PASSWORD=sua-senha
Nunca versione o .env real. Use .env.example como referência. Se faltar alguma chave, o backend imprime erro e encerra.

Backend — Reautenticação Automática

O proxy detecta sessão expirada e refaz o login, repetindo a requisição (até 3 tentativas).

Funções-chave

  • is_session_expired_response(r) — considera expirado: HTTP 401 ou HTTP 500 com corpo {"status":500,"message":"Ocorreu um erro inesperado..."}.
  • perform_proxy_request(method, target, body, platform) — loop de 3 tentativas com headers de auth; re-loga e continua se a resposta indicar sessão expirada.
  • build_auth_headers(...) — monta os headers de autenticação.
Histórico: o bug 500 — a API retorna 500 (e não 401) quando o token expira. O proxy repassava o erro ao frontend; agora trata 500 como sessão expirada e reautentica.

Status e online (regras)

  • Status OCPP — derivado de connectors[].lastStatus.status: Available → Disponível, Occupied/Charging → Ocupado, Faulted → Falha, etc.
  • Online — derivado de lastHeartbeatTimestamp: ≤3 min → Online, ≤10 min → Atrasado, >10 min → Offline.
  • Status e online são métricas independentes (ex.: estação pode estar "Disponível" mas "Offline").
  • formatToSaoPaulo(iso) — formata datas para o fuso America/Sao_Paulo.

Telas

Login (views/login/login.jsx)

Formulário de e-mail/senha. Envia para /login-proxy; em sucesso salva a sessão em localStorage (chave posmobi_session) e chama /set-session. O e-mail vem preenchido por padrão.

Dashboard (views/dashboard/dashboard.jsx)

  • 4 KPIs: Carregadores, Ativos, Ocupados, Com falha.
  • Gráfico de barras "Carregadores por modelo" (recharts).
  • Filtros completos: ChargeBox ID, Descrição, Modelo, Status, Online, Firmware, Cidade/UF, Ativo + botão Limpar.
  • Tabelas agrupadas por modelo com badge de status, ícone de online, botão Update de firmware (para estação Disponível), cidade/UF, último heartbeat e Ativo/Inativo.
  • Estações com falha: modal de logs com linhas destacadas (erros em vermelho) e causa extraída do log.
  • Carrega dados apenas na primeira visita da sessão (cache em módulo DASH_CACHE); botão ATUALIZAR força recarga.

Firmware (views/firmware/firmware.jsx)

  • Filtros idênticos ao dashboard + seletor de Conta.
  • Tabela de carregadores com seleção múltipla: ChargeBox ID, Descrição, Modelo, Status, Status FW, Firmware, Gateway.
  • Envio por tipo de firmware: Gateway (.bin), MCU (.hex), Completa (.enfs).
  • Se o modelo não tem URL cadastrada, abre modal "Vincular carregador de firmware".
  • Modal "Editar URL" (quase tela cheia): cadastro de carregadores/modelos com URL+Versão por tipo e grid "Vincular modelos".
  • Monitoramento em tempo real (10s) do status do upload via parse de logs OCPP; conclui quando todos atingem estado final (Installed, falha, Idle).
  • Persistência local dos blocos em backend/data/firmware.json (com migração do localStorage antigo posmobi_firmware_urls).

Histórico (views/firmware/history.jsx)

  • Resumo do período: atualizações e última atualização.
  • Gráfico de barras empilhadas "Versões de firmware por modelo" — cada barra é um modelo, o total é o nº de equipamentos, e cada segmento é uma versão de firmware (dados dos chargepoints atuais, filtrado pela conta).
  • Tabela paginada (10 por página) de atualizações: Carregador, Estação, Gateway (old→new), MCU (old→new), Atualizado em, Por, Tipo (Baseline/Atualização).
  • Filtros: Conta, Buscar, De, Até.

Log (views/log/log.jsx)

  • Fonte Cloud (Intelbras), seletor de conta, botão CARREGAR LOGS e DOWNLOAD (blob .txt).
  • Auto Refresh opcional (30s) — toggle.
  • Filtro por estação e busca por texto.
  • Visualizador estilo terminal com badges coloridos [ERROR]/[WARN]/[INFO].

Autenticação & Sessão

  1. App.jsx carrega a sessão do localStorage (posmobi_session).
  2. Sem sessão → mostra Login.
  3. Com sessão → setSession() sincroniza token/tenant com o backend e monta o roteador.
  4. Header tem menu Perfil → Logout (limpa sessão e volta ao login).
  5. Erros 401 nas chamadas disparam toasts "Sessão expirada" via isSessionExpired().

Firmware — Fluxo de Upload

  1. Carregadores são listados e filtrados (mesmos filtros do dashboard).
  2. Usuário seleciona estações e um tipo (Gateway/MCU/Completa).
  3. Para cada estação, a URL é resolvida pelo modelo via modelLinks → bloco → campo do tipo. Estações sem URL são direcionadas ao modal de vínculo.
  4. As estações são agrupadas por URL e enviadas via PUT /api/v1/operations/v1.6/update_firmware (mode v1.6, retries 1).
  5. Monitoramento a cada 10s: busca logs cloud e faz parse de FirmwareStatusNotification, BootNotification e gatewayInfo para atualizar status, versões e reboot.
  6. Quando todos os alvos atingem estado final, o monitoramento encerra com toast de conclusão.

Blocos de firmware (dados)

Cada bloco tem id, name e campos gateway, mcu, completa com {url, version}. Cada modelo é vinculado a um único bloco.
